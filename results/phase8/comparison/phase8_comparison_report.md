## 6. Why Repairs Did Not Convert Wrong ? Correct

The Phase 8 verification layer worked as designed (48.9% detection, 97.8% precision, 30 one-shot repairs),
but correctness stayed flat at 10%. The blocker is upstream: **the QueryPlan is wrong 84% of the time**,
and plan-based verification can only align SQL to the plan.

Plan audit (fresh planner run, 100/100, aligned vs frozen expected answers):

| Plan dimension | Alignment |
| :--- | :---: |
| LIMIT / top-N | 67% |
| Aggregation family | 66% |
| Required tables | 29% |
| All three core dimensions | 16% |

- Of the 30 repaired queries, only **3** had fully-aligned plans; of the 44 detected mismatches, only **4**.
- Typical planner failure modes:
  - Superlatives ("highest / most / busiest / peak") ? plan missing LIMIT 1 (67% limit alignment).
  - Composite metrics (cancellation rate, % delivered late, ARPU, LTV, median) ? single agg (COUNT/SUM) instead of the required ratio/average (66% agg alignment).
  - Table over-inclusion (customers/orders/geolocation joined for AOV, per-order, per-day queries) ? 71% of plans carry extra tables; repairs then add joins for missing-but-unneeded tables, causing fan-out.
- Result flips came entirely from LLM variance, not repairs: improved q001/q012, regressed q017/q036 � none repaired.

## 9. Conclusion & Recommendation

- The plan-alignment verifier + one-shot repair pipeline is validated and measurement-ready (detection
  precision 97.8%, FP repair rate 6.7%, programmatic repairs free).
- Correctness is capped by planner quality (16% all-core plan alignment). Next phase should target:
  1. Planner: superlative ? LIMIT 1; composite/ratio metrics ? correct aggregation; required-table pruning.
  2. Harness: add value-set equivalence (ignoring column names) as a secondary correctness metric.
  3. Re-run after planner fixes to measure the repair-to-correct conversion enabled by aligned plans.
